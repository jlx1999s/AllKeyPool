# KeyPool 开发文档

这份文档用于记录当前实现状态和下一步施工顺序。开源读者可以看根目录的 `README.md`、`ROADMAP.md` 和 `CONTRIBUTING.md`；我们后续实现时以本文为阶段清单。

## 当前技术栈

- Node.js >= 22.5
- TypeScript strict mode
- npm workspaces
- Fastify 5
- Pino structured logging
- Zod config validation
- YAML config
- SQLite (`node:sqlite`) 可选持久化
- Vitest

### 顺带修复

`renderAdminPanelHtml` 之前在模板字符串里写 `"\n"` 字面 JS 字符串,经 backtick template 输出到 HTML 后,`\n` 变成真换行导致 `<script>` 解析失败,auth 表单 submit 监听器根本没注册,表现为"输 token 进不去"。修法:用 `String.fromCharCode(10)` 替代。另一个类似 bug 是正则字面量 `/^#\/?/` 里的 `\/` 被 backtick 吞掉,改用 `[^/]` 风格。

## Phase 4：模拟 Key 池与可观测性

状态：已完成（v0.2 的可观测子集已落地）。

这一阶段的目标是：**在零外部依赖的前提下，让调度、限流、重试、故障注入可被复现、可被验证、可被肉眼看见**。它服务于本仓库的"演示 / 测试 / 调优"需求，不是新增对外能力。

入口：

```bash
KEYPOOL_CONFIG=./config/keypool.fake.yaml KEYPOOL_FAKE_PROVIDER=1 npm run dev
```

或者在已经运行的服务里通过 `GET /admin/api/state` 的 `fakeProvider` 字段确认是否处于 fake 模式。

已交付：

- `FakeOpenAIAdapter`（`apps/api/src/providers/fake/fake-adapter.ts`）
  - 实现 `ProviderAdapter`，不发起任何 HTTP 请求
  - 响应体 OpenAI 兼容，带 `servedBy`（keyId 末 4 位）和 `keyId` 字段
  - `checkHealth` 始终 healthy
  - `normalizeError` 与 `OpenAIAdapter` 行为对齐
  - 暴露 `getLastOutcome(keyId)` 供调试
- 故障脚本 DSL（`apps/api/src/providers/fake/fake-script.ts`）
  - 4 种内置策略：`sequence` / `periodic` / `burstRateLimit` / `probability`
  - 5 种 outcome：`ok` / `rate_limited` / `server_error` / `auth_failed` / `timeout`
  - outcome 可带 `latencyMs` 在响应前再注入延迟
- YAML 配置 DSL（`apps/api/src/providers/fake/fake-script-dsl.ts`）
  - 字符串 spec：`sequence(ok, 429, 500)` / `periodic(period=3, rate_limited)` / `burst(windowMs=1000, allowed=2, outcome=rate_limited)` / `probability(p=0.1, outcome=server_error, seed=42)`
  - 优先级：key 级 `script` > provider 级 `script`
- `UsageRecorder` 接口与 `InMemoryUsageRecorder`（`apps/api/src/core/usage/usage-recorder.ts`）
  - 每 key 维护容量 64 的环形 timeline
  - 记录成功与失败，包含 `latencyMs` / `statusCode` / `errorCode` / `requestId`
- `ProviderRequestExecutor` 新增 `onAttemptSuccess` 回调，附 `latencyMs`
- `app.ts` 装配 UsageRecorder，分别在成功/失败钩子里写入
- `GET /admin/api/state` 在每个 key 上回填 `usage` 摘要
- `GET /admin/api/keys/:id/usage?limit=N` 返回单 key 的 timeline 详情
- 静态演示配置 `config/keypool.fake.yaml`
  - 6 个 provider / 6 个 pool，覆盖 round_robin、weighted_round_robin、周期性 429、突发限流、概率 500、quota 限流
- `KEYPOOL_FAKE_PROVIDER=1` 环境变量开关，默认关闭
- Fake 模块 + 端到端 e2e 测试

当前边界：

- 故障脚本在 `buildApp` 启动时构造，运行中不热更新（改 yaml 需重启）。
- 默认内存模式下 UsageRecorder 是进程内记录，重启即丢；启用 SQLite 后 usage records 持久化。
- `requestId` / `pool` / `strategy` 在 onAttemptSuccess 路径下记为 `unknown`（executor 签名未扩展），仅 `keyId` / `latencyMs` 准确。
- `getLastOutcome` 仅做调试用，不暴露给 HTTP API。
- 暂无历史用量导出、Prometheus 指标。

## Phase 4.5：模拟用户入口（Demo Runner）

状态：已完成。

在 Phase 4 的可观测性之上，加一个"模拟真实用户"的入口。运维、QA、性能调优都不再需要 grep 日志，所有重试/调度/限流行为都能在一个 HTTP 响应里看到完整链路。

入口：

```text
POST /_demo/chat
```

鉴权与 `/admin/api/*` 共用 admin token。

### 请求

```jsonc
{
  "model": "fake-ok",        // 必填
  // 三种消息描述方式（优先级 messages > turns > prompt）：
  "messages": [{ "role": "user", "content": "..." }],  // OpenAI 标准
  "turns": ["one", "two", "three"],                    // 多轮 shortcut
  "prompt": "hi",                                       // 单轮 shortcut
  "count": 6,                                           // 把同一份消息重发 N 次
  "intervalMs": 50,                                     // 重发间隔
  "sessionId": "stuck-1",                               // sticky session（可选）
  "strategy": "round_robin"                             // 覆盖 pool 默认
}
```

若同时传 `turns` 和 `count`，`count` 优先；当 `count` 为默认 1 时自动取 `turns.length`。

### 响应

```jsonc
{
  "sessionId": "stuck-1",
  "model": "fake-ok",
  "pool": "ok_pool",
  "provider": "ok",
  "startedAt": "2026-07-06T08:00:00.000Z",
  "totalDurationMs": 87,
  "results": [
    {
      "turn": 3,
      "requestId": "...",
      "status": 200,
      "provider": "rl",
      "pool": "rl_pool",
      "keyId": "rl-prod-2",
      "servedBy": "d-2",
      "latencyMs": 23,
      "attempt": 2,
      "attempts": [
        { "attempt": 1, "keyId": "rl-prod-2", "outcome": "error", "statusCode": 429, "errorCode": "rate_limited", "latencyMs": 11 },
        { "attempt": 2, "keyId": "rl-prod-3", "outcome": "success", "statusCode": 200, "latencyMs": 12 }
      ],
      "responseText": "[fake:d-3] ping"
    }
  ],
  "summary": {
    "total": 4, "success": 4, "failed": 0,
    "avgLatencyMs": 11, "p50LatencyMs": 11, "p95LatencyMs": 12,
    "distinctKeys": 3,
    "distinctKeyIds": ["rl-prod-1", "rl-prod-2", "rl-prod-3"]
  }
}
```

### 关键设计

- `attempts` 数组是 `executor.attemptSink` 收集出来的 per-call 完整重试链。
- sticky session：调用方传 `sessionId` 时，第一次命中的 keyId 被钉死，后续轮次通过 `excludedKeyIds` 排除其他 key。这验证了未来的 sticky 策略接口。
- `summary` 直接由 results 派生，含 success / failed / avg / p50 / p95 / distinct keys。
- 不依赖 `app.inject`，直接调 `app.providerRequestExecutor.execute()`，以拿到 attempts 数组。
- 与 fake 池配合，零外部依赖即可端到端演示。

### 面板：Demo Runner 区块

`/admin` 顶部新增 "Demo Runner" section：

- 模型下拉（自动从已注册 pool 抽取）
- 多轮消息输入（+ / − 按钮增删）
- sessionId / count / intervalMs / strategy 字段
- 三个按钮：单轮 / 多轮 / 压测
- 跑完展示：summary metric 卡（7 个）+ 逐轮结果表（每行 hover 显示 attempts 链）
- 实时状态 pill：idle / running… / done / error

### 顺带修复

`ProviderRequestExecutor` 之前会把调用方传入的 `excludedKeyIds` 覆盖为自己的 `attemptedKeyIds`，导致 sticky 失效。修法：把两者合并，确保重试不破坏调用方意图。

### 当前边界

- 暂不支持流式（chat.completion.stream）。
- 暂不支持中途取消（count=N 跑起来就要跑完）。
- `responseText` 只取第一段（最多 200 字符）。
- sticky session 是"用 excludedKeyIds 模拟"——不是真正的 session-aware 策略，等未来 v0.3 sticky strategy 落地。

## Phase 5：SQLite 持久化

状态：基础完成。

目标：在不引入外部数据库服务的前提下，让生产管理后台的运行时 key、用量记录、健康事件和审计日志可以跨进程重启保存。

启用方式：

```bash
KEYPOOL_STORAGE=sqlite KEYPOOL_SQLITE_PATH=./data/keypool.db npm run dev
```

设计原则：

- 默认仍为 `memory`，方便本地开发和测试。
- SQLite 是默认单机生产存储，不替代后续 Postgres / Redis 方案。
- YAML 仍是 bootstrap 配置；SQLite 保存运行时状态。
- 业务层只依赖 `ApiKeyRepository` / `UsageRecorder` / `HealthEventRecorder` / `AuditLogRecorder` 接口。

已交付：

- `createStorage()` 存储工厂，支持 `memory` / `sqlite`
- `openSqliteDatabase()`，自动创建目录并执行轻量 migration
- `SqliteApiKeyRepository`
  - 持久化 key value、provider、pool、weight、status、failureCount
  - 设置 `KEYPOOL_ENCRYPTION_KEY` 后使用 AES-256-GCM 加密 key value
  - 持久化 `rpmLimit` / `dailyRequestLimit`
  - 持久化 `lastUsedAt` / `coolingDownUntil`
  - 持久化 `metadata.runtimeConfig`
  - 启动时用 YAML seed 缺失 key，但不覆盖 DB 中已有 key 状态
- `SqliteUsageRecorder`
- `SqliteHealthEventRecorder`
  - Usage 支持按 `route` / `model` / `pool` / `provider` / `keyId` / `outcome` / `errorCode` 过滤
  - Health Events 支持按 `type` / `level` / `requestId` / `provider` / `keyId` / `code` 过滤
- Admin Usage 页面展示最近请求事件和健康事件，并支持按 outcome / provider / keyId / type / level 直接过滤，方便排查供应商失败、限流和 key 冷却。
- `SqliteAuditLogRecorder`
  - 持久化管理操作：`key_created` / `key_updated` / `key_status_changed` / `key_deleted`
  - 记录 actor、target、outcome、message 和安全 metadata
  - 支持按 `action` / `outcome` / `targetType` / `targetId` / `actorType` / `actorId` 过滤
  - 不写入 API key 明文
- App 启动时根据持久化 key 的 `runtimeConfig` 恢复 provider registry 和 pool routing
- `/admin/api/state` 返回 `storage.kind`
- `GET /admin/api/audit-logs?limit=N&action=key_status_changed&outcome=success&targetId=...`
- Settings 页面展示最近审计日志，并支持按 action / outcome / targetId 基础过滤
- SQLite repository 单元测试
- SQLite app persistence 测试：通过 admin API 新增 key，关闭 app，再用同一个 db 启动并恢复 key/provider/pool

当前边界：

- 当前 SQLite 依赖 Node 内置 `node:sqlite`，Node 运行要求提高到 `>=22.5`。
- SQLite 当前保存 runtime keys / usage / health events / audit logs，不保存完整 YAML config diff。
- Admin 删除 key 会删除 DB 中 key，但不会清理历史 usage / health event / audit log。
- SQLite key value 支持 `KEYPOOL_ENCRYPTION_KEY` 加密；后续仍可扩展 KMS/secret manager。
- 审计日志当前覆盖管理台 key 操作；全请求级审计 / trace 仍属于后续 OpenTelemetry 或 request audit。
- 多实例部署仍需要 Postgres + Redis；SQLite 适合单机部署。

3. 补充 TPM 统计入口与按 key 的吞吐监控。
4. 支持 Postgres 存储实现。
5. 支持生产级 RBAC，并把 audit actor 从统一 `admin` 替换为真实主体。
